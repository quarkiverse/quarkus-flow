= OpenTelemetry
:page-role: howto

Quarkus Flow provides built-in OpenTelemetry instrumentation, enabling observational insight into your workflow executions.

[IMPORTANT]
====
This functionality is tech preview and is currently best suited for straight-through workflow executions.
====

== Configuring OpenTelemetry

To enable OpenTelemetry, you must add the following dependency to your project:

[source,xml]
----
<dependency>
  <groupId>io.quarkiverse.flow</groupId>
  <artifactId>quarkus-flow-opentelemetry</artifactId>
</dependency>
----

Once the dependency is added, workflow executions will start producing OpenTelemetry information automatically.

[NOTE]
====
* The `quarkus-flow-opentelemetry` extension is built on top of `quarkus-opentelemetry`. All configurations related to trace exporters and OTLP endpoints are managed via the standard Quarkus OpenTelemetry extension. For full configuration details, refer to the link:https://quarkus.io/guides/opentelemetry[Quarkus OpenTelemetry Guide].

* Setting either `quarkus.otel.enabled=false` or `quarkus.otel.traces.enabled=false` automatically disables the Quarkus Flow OpenTelemetry instrumentation.
====

To disable Quarkus Flow OpenTelemetry specifically, set `quarkus.flow.otel.enabled=false` (in application.properties or as a system/environment property at startup), or simply remove the dependency.

== Produced Spans

Quarkus Flow generates two main types of spans to trace workflow execution:

**Workflow Spans**: Represent the end-to-end lifecycle of a workflow instance, from its initial trigger to completion, failure or cancellation.

**Task Spans**: Represent the execution of a workflow task within the context of a parent workflow.

Task spans automatically reflect the workflow hierarchy, attaching as children to either the parent workflow span or another task span.

=== Workflow Spans

Workflow spans represent the overall execution of a workflow instance and includes the following information:

* Span Name Format: `workflow.execute <workflow-name>`
* Example, `workflow.execute order-processing`

[cols="2,2,4",options="header"]
|===
| Attribute Name | Type | Description

| `flow.application.id`
| String
| Identifier of the Quarkus Flow application.

| `flow.workflow.name`
| String
| Name of the executed workflow.

| `flow.workflow.instance.id`
| String
| Unique execution id generated for this specific workflow run.

| `flow.workflow.namespace`
| String
| Namespace of the executed workflow.

| `flow.workflow.version`
| String
| Version of the executed workflow.

| `gen_ai.operation.name`
| String
| `invoke_agent`. Only present when the workflow itself is an agent: a workflow generated from a LangChain4j agentic annotation, or one that opts in through its document metadata. See <<genai-semantic-conventions>>.

| `gen_ai.agent.name`
| String
| Name of the agent. Only present when the workflow itself is an agent.

| `gen_ai.agent.description`
| String
| The workflow's `document.summary`. Only present when the workflow itself is an agent and the summary is not blank.
|===

=== Task Spans

Task spans represent the execution of a workflow task and includes the following information:

* Span Name Format: `task.execute <task-name>`
* Example, `task.execute Submit Order`

[cols="2,2,4",options="header"]
|===
| Attribute Name | Type | Description

| `flow.application.id`
| String
| Identifier of the Quarkus Flow application.

| `flow.workflow.name`
| String
| Name of the executed parent workflow.

| `flow.workflow.instance.id`
| String
| Unique execution id of the parent workflow execution.

| `flow.workflow.namespace`
| String
| Namespace of the executed parent workflow.

| `flow.workflow.version`
| String
| Version of the executed parent workflow.

| `flow.task.name`
| String
| Name of the executed task.

| `flow.task.type`
| String
| Type of executed task. Can be any of the following values: `do`, `emit`, `for`, `fork`, `listen`, `raise`, `run`, `set`, `switch`, `try`, `wait`, `call_http`, `call_asyncapi`, `call_grpc`, `call_openapi`, `call_a2a`, `call_function`.

| `flow.task.id`
| String
| Identifier of the executed task.

| `flow.task.iteration`
| Integer
| Number of the current task iteration.

| `flow.task.retrying`
| Boolean
| True if the task execution is a retry of a previous failing attempt, false in any other case.

| `flow.task.retry_attempt`
| Integer
| Number of retry if the task execution is a retry of a previous failing attempt, 0 in any other case.

| `gen_ai.operation.name`
| String
| `invoke_agent`. Only present on tasks created with the Java DSL `agent(..)`. See <<genai-agent-tasks>>.

| `gen_ai.agent.name`
| String
| Name of the invoked agent, which is the task name. Only present on tasks created with the Java DSL `agent(..)`.
|===

[TIP]
====
Use meaningful names for your workflows and tasks. Because span names and attributes directly reflect your workflow definitions, well-named tasks result in much cleaner and readable traces in your telemetry UI.
====

== Trace Context Propagation

=== Spans created inside a task

While a Java function call task runs, its `task.execute` span is the current span. These are the tasks created with the Java DSL's `function(..)`, `consume(..)` and `agent(..)`. Spans the task creates, such as REST client calls, JDBC queries, LangChain4j AI service calls or your own `Span` instances, become children of the task span. They stay in the workflow's trace.

[NOTE]
====
HTTP, OpenAPI, gRPC, A2A, AsyncAPI and MCP call tasks are not covered yet. Their outgoing request spans are not children of their task span:

* When the workflow is started from an incoming request, they are children of that request's span.
* Otherwise, they start their own trace.
====

To keep the task span from being current inside task bodies, set:

[source,properties]
----
quarkus.flow.otel.task-span-current=false
----

With this setting the task span is still recorded, but `Span.current()` inside the task body is whatever was current on the executing thread.

[[agentic-workflows-trace-context]]
=== Agentic workflows

When a task invokes a LangChain4j agentic system (`@SequenceAgent`, `@ParallelAgent`, `@ConditionalAgent`, `@LoopAgent`) through `quarkus-flow-langchain4j`, Quarkus Flow passes the trace context through the whole run:

* The workflow generated for the agentic system becomes a child of the invoking task.
* Each agent's AI service call becomes a child of the task that ran it, including agents run in parallel on LangChain4j's executor.

The whole run is a single trace:

[source,text]
----
workflow.create my-workflow
└── workflow.execute my-workflow
    └── task.execute runAgents
        └── workflow.create intake-agents
            └── workflow.execute intake-agents
                ├── task.execute classify-0
                │   └── langchain4j.aiservices.ClassifierAgent.classify
                └── task.execute extract-1
                    └── workflow.create extraction-agent
                        └── workflow.execute extraction-agent
                            └── task.execute parallel
                                ├── task.execute details-0
                                │   └── langchain4j.aiservices.DetailsAgent.details
                                └── task.execute summarize-1
                                    └── langchain4j.aiservices.SummaryAgent.summarize
----

[[genai-semantic-conventions]]
== GenAI Semantic Conventions

Quarkus Flow types the spans of agent invocations according to the OpenTelemetry link:https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md[GenAI agent span conventions]. GenAI-aware observability backends can then classify these spans as agents. Backends that keep only spans carrying a `gen_ai.*` attribute also keep them, even when the span ends in a later export batch than its AI children.

Which span is typed depends on what the agent is:

* When the workflow itself is an agent, its `workflow.execute` span is typed. This covers <<genai-generated-workflows,generated agentic workflows>> and <<genai-own-workflows,workflows that opt in>>.
* When a task invokes an agent, its `task.execute` span is typed. This covers <<genai-agent-tasks,tasks created with the Java DSL `agent(..)`>>.

A typed span gets these attributes:

* `gen_ai.operation.name`: `invoke_agent`
* `gen_ai.agent.name`: the agent name
* `gen_ai.agent.description`: the workflow's `document.summary`, when it is not blank (workflow spans only)

Span names and all `flow.*` attributes are kept. `workflow.create` spans and all other task spans are never typed: a plain workflow step is not an agent, and the conventions define no operation name for it.

[[genai-generated-workflows]]
=== Generated agentic workflows

The workflows that `quarkus-flow-langchain4j` generates for `@SequenceAgent`, `@ParallelAgent`, `@ConditionalAgent` and `@LoopAgent` are typed automatically, in every launch mode. The agent name is the annotation's `name`, or the annotated method's name when `name` is not set. For the example in <<agentic-workflows-trace-context>>, `workflow.execute intake-agents` has `gen_ai.agent.name=process` and `workflow.execute extraction-agent` has `gen_ai.agent.name=extract`.

Workflows built at runtime with `FlowAgentsBuilderService` are typed too. Their agent name is the simple name of the agent interface (`UntypedAgent` for untyped agents).

[[genai-own-workflows]]
=== Typing your own workflows

Any other workflow opts in by setting the `io.quarkiverse.flow.agent.name` key in its document metadata. Its value becomes `gen_ai.agent.name`. Workflows without this key are never typed.

With the Java DSL:

[source,java]
----
@Override
public Workflow descriptor() {
    return workflow("triage")
            .document(d -> d.summary("Triage an incoming request")
                    .metadata(m -> m.metadata("io.quarkiverse.flow.agent.name", "triage")))
            .tasks(/* ... */)
            .build();
}
----

In a YAML definition:

[source,yaml]
----
document:
  dsl: '1.0.0'
  namespace: support
  name: triage
  version: '1.0.0'
  summary: Triage an incoming request
  metadata:
    io.quarkiverse.flow.agent.name: triage
----

[[genai-agent-tasks]]
=== Agent tasks

Tasks created with the Java DSL `agent(..)` are agent invocations. Their `task.execute` span is typed, and the task name becomes `gen_ai.agent.name`. The workflow containing them is not typed, unless it is an agent itself.

[source,java]
----
@Override
public Workflow descriptor() {
    return workflow("newsletter")
            .tasks(agent("draftAgent", drafter::draft, NewsletterRequest.class), // <1>
                    function("publish", publisher::publish, Draft.class))      // <2>
            .build();
}
----
<1> `task.execute draftAgent` has `gen_ai.operation.name=invoke_agent` and `gen_ai.agent.name=draftAgent`.
<2> `task.execute publish` is not typed.

Name your agent tasks: an unnamed `agent(..)` task gets a generated name such as `function-0`, which then becomes the agent name.

=== Limitations

* The GenAI semantic conventions are still incubating, so attribute names may change in future versions of the conventions and of Quarkus Flow.
* `gen_ai.provider.name` is not set, although the conventions require it on `invoke_agent` spans. A workflow that orchestrates several agents has no single provider. The model call spans beneath it, such as LangChain4j's chat spans, carry the provider of each call.
