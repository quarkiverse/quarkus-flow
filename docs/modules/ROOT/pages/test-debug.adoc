= Test and debug workflows
:page-role: howto
include::includes/attributes.adoc[]

Because Quarkus Flow is deeply integrated with the Quarkus ecosystem, testing your workflows is as straightforward as testing any standard Java application.

This guide shows how to:

* Write fast unit tests for workflow logic (both Java DSL and YAML definitions).
* Record and assert on workflow lifecycle events with the `quarkus-flow-testing` module.
* Write end-to-end integration tests for REST resources that trigger workflows.
* Verify automatic HTTP error mapping (RFC 7807 Problem Details).
* Enable tracing and structured logging to debug test executions.

== Prerequisites

* A Quarkus application with xref:getting-started.adoc[Quarkus Flow set up].
* JUnit 5 tests using `@QuarkusTest` (or `QuarkusExtensionTest` if writing extension tests).
* REST Assured (included in `quarkus-junit5-mockito` or `quarkus-rest-client`) for HTTP endpoint testing.
* The `quarkus-flow-testing` test dependency if you want to record and assert on workflow lifecycle events, not just the final output (see below).

== 2. Record and assert on workflow events

Asserting on the final `WorkflowModel` (as in section 1 above) is enough for simple workflows, but for anything with multiple tasks, retries, or branching, you often want to verify *how* the workflow got there — which tasks ran, in what order, and whether any of them failed.

The `quarkus-flow-testing` module provides exactly that: an injectable `WorkflowEventStore` that records every workflow and task lifecycle event produced during a test, plus a `FlowAssertions` entry point with fluent, AssertJ-style assertions on top of it.

Add the module as a test dependency:

[source,xml]
----
<dependency>
    <groupId>io.quarkiverse.flow</groupId>
    <artifactId>quarkus-flow-testing</artifactId>
    <scope>test</scope>
</dependency>
----

=== 2.1 Record events with `@QuarkusFlowTest`

Annotate the test class (or method) with `@QuarkusFlowTest` to capture every event emitted while the annotated test runs. `WorkflowEventStore` is a regular CDI bean, so you can inject it too, but `FlowAssertions.assertThat()` resolves it for you:

[source,java]
----
include::{examples-dir}test/HelloWorkflowEventRecordingTest.java[tag=should_record_and_assert_workflow_events]
----
<1> `@QuarkusFlowTest` clears the store immediately before this test runs. The default scope is `QuarkusFlowTest.Scope.PER_METHOD`, so each test method starts with its own empty session.
<2> `FlowAssertions.assertThat(instance)` looks up the CDI-managed store, snapshots the events recorded for just this workflow instance, and wraps both the instance and that snapshot in a `WorkflowInstanceAssert`...
<3> ...then asserts on the exact lifecycle sequence: workflow started, the `set` task started and completed, workflow completed.

[NOTE]
Use `@QuarkusFlowTest(scope = QuarkusFlowTest.Scope.PER_CLASS)` when several `@Test` methods in the same class should share one continuous recording session: the store is cleared once before the first method runs, and again after the whole class finishes, but *not* between individual methods. This is useful for multi-step scenarios split across several test methods — just remember to filter with `filteredByInstanceId(...)` if more than one method in the class starts its own workflow instance, since events accumulate across all of them in the same buffer.

[IMPORTANT]
`FlowAssertions.assertThat()` and `FlowAssertions.assertThat(workflowInstance)` resolve the `WorkflowEventStore` from CDI, so they only work inside a running container — a `@QuarkusTest`. They throw `IllegalStateException` if called outside one.

=== 2.2 Fluent assertions with `FlowAssertions`

`WorkflowEventStore` also exposes `getByInstanceId`, `getByType`, and `getByTaskName` directly if you'd rather work with a plain `List<RecordedEvent>`, but `FlowAssertions` saves you the manual `.stream().filter(...)` boilerplate and gives you AssertJ-quality failure messages:

[source,java]
----
FlowAssertions.assertThat(instance)                      // a WorkflowInstanceAssert snapshotting instance's events
        .hasStatus(WorkflowStatus.COMPLETED)              // assert on the instance's own state...
        .hasEventType(EventType.WORKFLOW_COMPLETED)       // ...and on its recorded events, in the same chain
        .doesNotHaveEventType(EventType.WORKFLOW_FAILED)
        .hasTaskEvent("sendEmail", EventType.TASK_COMPLETED); // a specific task's outcome

// equivalent event assertions, filtering the whole store manually:
FlowAssertions.assertThat()
        .filteredByInstanceId(instance.id())
        .hasEventType(EventType.WORKFLOW_COMPLETED);
----

`WorkflowInstanceAssert` combines two things: assertions on the `WorkflowInstance` itself (like `hasStatus(...)`) and assertions on the events recorded for it, delegated to the same vocabulary as `RecordedEventListAssert` (`hasEventType`, `doesNotHaveEventType`, `hasEventTypes`, `hasEventTypesExactly`, `hasTaskEvent`). Call `.events()` to drop down to the full `RecordedEventListAssert` API (e.g. `extracting(...)`, `first()`) for anything not covered directly.

`filteredByType(...)` and `filteredByTaskName(...)` are also available directly on `WorkflowEventStoreAssert`, alongside `all()` if you want every recorded event regardless of instance. Every `filteredByX` method returns a (possibly empty) result rather than asserting anything by itself — chain `.isNotEmpty()` or one of the `hasEventType*`/`hasTaskEvent` assertions to actually assert something.

[TIP]
`@QuarkusFlowTest` handles clearing the recording session automatically for both scopes, so you never need to call `eventStore.clear()` yourself inside a `@QuarkusFlowTest`-annotated test.

== 3. Test REST resources that invoke workflows

Most real-world applications expose workflows via HTTP endpoints. You should write integration tests using REST Assured to verify both the REST layer and the workflow execution.

Assume you have a modern, reactive JAX-RS resource like this:

[source,java]
----
import io.quarkiverse.flow.Flow;
import io.serverlessworkflow.api.WorkflowInstance;
import io.smallrye.common.annotation.Identifier;
import io.smallrye.mutiny.Uni;
import jakarta.inject.Inject;
import jakarta.ws.rs.GET;
import jakarta.ws.rs.Path;
import jakarta.ws.rs.QueryParam;
import java.util.Map;

@Path("/echo")
public class EchoResource {

    @Inject
    @Identifier("org.acme.EchoWorkflow")
    Flow echoFlow;

    @GET
    public Uni<Map<String, Object>> echo(@QueryParam("name") String name) {
        String finalName = (name != null && !name.isBlank()) ? name : "Duke";

        return echoFlow.startInstance(Map.of("name", finalName))
                       .map(WorkflowInstance::output); // Return final workflow state
    }
}
----

You can test this end-to-end using REST Assured:

[source,java]
----
import static io.restassured.RestAssured.given;
import static org.hamcrest.Matchers.equalTo;

import io.quarkus.test.junit.QuarkusTest;
import org.junit.jupiter.api.Test;

@QuarkusTest
class EchoResourceTest {

    @Test
    void should_echo_name_over_http() {
        given()
            .queryParam("name", "John")
        .when()
            .get("/echo")
        .then()
            .statusCode(200)
            .body("message", equalTo("Hello, John!"));
    }
}
----

== 4. Verify HTTP error mapping

If your workflow includes an HTTP or OpenAPI task that fails (e.g., calling a secured external API without credentials), Quarkus Flow automatically translates the internal `WorkflowException` into an RFC 7807 Problem Details HTTP response.

You should write tests to verify this mapping behaves correctly for your clients:

[source,java]
----
import static io.restassured.RestAssured.given;
import static org.hamcrest.Matchers.equalTo;

import io.quarkus.test.junit.QuarkusTest;
import org.junit.jupiter.api.Test;

@QuarkusTest
class CustomerProfileResourceTest {

    @Test
    void should_map_workflow_exception_to_problem_details() {
        given()
            .queryParam("customerId", "unauthorized-user")
        .when()
            .get("/customer/profile")
        .then()
            .statusCode(401)
            .body("type", equalTo("https://open-workflow-specification.org/spec/1.0.0/errors/communication"))
            .body("title", equalTo("HTTP 401 Unauthorized"))
            .body("status", equalTo(401));
    }
}
----

[TIP]
For this automatic error mapping to work, your JAX-RS resource **must be reactive** (returning a `Uni` or `CompletionStage`). If you block the thread with `.await().indefinitely()`, Java wraps the error in an `ExecutionException`, and the standard Quarkus mapper will not catch it.

== 5. Enable tracing for debugging tests

When a complex workflow test fails, it can be hard to know exactly which task broke. You can enable Quarkus Flow's execution tracer specifically for your test runs to see exactly how the engine routed the data.

Add this to your `application.properties`:

[source,properties]
----
# Enable tracing only during test execution
%test.quarkus.flow.tracing.enabled=true
----

When you run `mvn test`, the console will output a clear, linear history of every task start, completion, and failure for that specific workflow execution.

*(For advanced structured logging with JSON and MDC fields, see xref:tracing.adoc[Enable distributed tracing]).*

== 6. Tips for reliable workflow tests

* **Mock External Dependencies:** Avoid calling real external APIs in unit tests. Use tools like `WireMock` or `Testcontainers` to stub the endpoints your HTTP tasks call.
* **Mock AI Agents:** If you are testing xref:langchain4j.adoc[LangChain4j workflows], mock the AI provider to avoid flaky tests caused by network latency or non-deterministic LLM generations.
* **Keep workflows focused:** It is much easier to write exhaustive tests for a workflow that has a single responsibility than it is to test a massive, sprawling business process. Break complex logic into smaller subflows.
