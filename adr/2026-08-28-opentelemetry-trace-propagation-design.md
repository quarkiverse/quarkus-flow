# OpenTelemetry Trace Propagation Across CloudEvent-Triggered Workflow Execution - Design Specification

**Date:** 2026-08-28
**Status:** Proposed
**Issue:** [#908](https://github.com/quarkiverse/quarkus-flow/issues/908)
**Reported via:** [Discussion #902](https://github.com/quarkiverse/quarkus-flow/discussions/902) ("Little bit lost with opentelemetry tracing context")

## Overview

A user running 1.0.0 with OpenTelemetry enabled reported that CloudEvent-triggered workflows produce **two disconnected traces** in their trace visualizer instead of one continuous trace: one for the inbound HTTP request, and a second, unrelated trace (new random trace ID) for the workflow execution itself. Task-level logs inside the workflow engine consistently show empty `traceId`/`spanId`/`parentId` in the MDC, even though the HTTP-layer logs show them correctly.

Investigation traced the immediate cause to `quarkus-reactive-messaging-http`, the connector used in the reported setup: it never makes an OTel `Context` current for the messages it delivers, so there is no live trace context for Quarkus Flow to inherit by the time the workflow engine dispatches the event. That gap lives in the connector, not in Quarkus Flow, and is tracked upstream as [quarkiverse/quarkus-reactive-messaging-http#442](https://github.com/quarkiverse/quarkus-reactive-messaging-http/issues/442) (see Non-Goals) — fixing it is out of this repo's control.

Independent of that upstream fix, the same investigation surfaced three related gaps, real regardless of which connector is involved: the workflow engine has no fallback for reconstructing a parent trace when no live `Context` is available, trace context isn't persisted across restarts so resumed instances lose tracing entirely, and flow-level logs are never correlated to whatever span is active. Of these, the first and third are entirely within Quarkus Flow's control; the second needs a new extension point from the vendored SDK — there's currently no supported way for a `WorkflowExecutionListener` to persist cross-cutting instance data across a restart without polluting the workflow's own data model — and is tracked upstream as [open-workflow-specification/sdk-java#1645](https://github.com/open-workflow-specification/sdk-java/issues/1645). This ADR proposes closing the first and third problems now, together with a CloudEvent `traceparent` extraction fallback that restores one continuous trace for CloudEvent-triggered workflows without waiting on the upstream connector fix, and commits Quarkus Flow's side of the second once the upstream SDK issue lands.

## Non-Goals

- Rewriting or forking the vendored `io.serverlessworkflow` SDK — `WorkflowMutableInstance` and `AbstractTypeConsumer` have no OTel awareness by design; work stays entirely within Quarkus Flow's own extension code (`core/runtime`, `opentelemetry/runtime`, `messaging/runtime`, `persistence/*`).
- Fixing propagation inside third-party connectors — `quarkus-reactive-messaging-http`, the connector used in the reported bug, never makes an OTel `Context` current for the messages it delivers in the first place, which is the confirmed root cause of the two-disconnected-traces symptom. That gap is out of this repo's control and is tracked upstream as [quarkiverse/quarkus-reactive-messaging-http#442](https://github.com/quarkiverse/quarkus-reactive-messaging-http/issues/442). Quarkus Flow's contribution here is limited to the CloudEvent `traceparent` extraction fallback (Phase 1 below), which works regardless of whether the receiving connector has any OTel instrumentation — see Alternatives Considered for why a connector/executor-level fix was considered and rejected as in-scope work for this ADR.

## Context

### Problem 1 — Workflow engine mints a brand-new root trace

`OTelWorkflowExecutionListener.onWorkflowStarted` builds the workflow's root span with `Context.current()` as parent, unconditionally. For CloudEvent-triggered workflows arriving via connectors that never establish a live OTel `Context` in the first place (confirmed for `quarkus-reactive-messaging-http` — see Non-Goals), `Context.current()` is empty (`Context.root()`) by the time the workflow engine dispatches the event, so `SpanBuilder.setParent(Context.root())` behaves like `setNoParent()` — OTel mints a fresh random trace ID. There is no fallback that reconstructs a parent context from anything about how the workflow was triggered.

**How a trace reaches a CloudEvent at all — the relation between OTel trace context and a CloudEvent.** 
These are two different things joined by one spec. OTel trace context (a W3C `traceparent`: trace ID + parent span ID + flags) is what OTel propagates in-process via `Context` and, across HTTP, via the `traceparent` header. 
A CloudEvent is the event envelope. 
The bridge is the CloudEvents [Distributed Tracing extension](https://github.com/cloudevents/spec/blob/main/cloudevents/extensions/distributed-tracing.md): it defines `traceparent`/`tracestate` as **CloudEvent extension attributes** whose values are exactly the W3C Trace Context of the operation that produced the event. So "the workflow inherits the trigger's trace" concretely means "the producer stamped `traceparent` onto the CloudEvent per that extension, and the workflow engine reads it back." 
Quarkus Flow already writes those attributes on the **outbound** side — `OTelEmittedEventDecorator` injects the active span context into every emitted CloudEvent via `TextMapPropagator.inject`. 
Phase 1 is the missing **inbound** half of the same contract; without it, a CloudEvent that arrives carrying a perfectly good `traceparent` still starts a disconnected trace.

Note that `onWorkflowStarted`/`WorkflowStartedEvent` (`io.serverlessworkflow.impl.lifecycle.WorkflowStartedEvent`) has no `CloudEvent` field — a workflow instance can be started from arbitrary input (`String`, `Integer`, a domain object, a `CloudEvent`-derived model, ...), not just CloudEvents, so there is no "the triggering CloudEvent" object reachable at this point, and nothing on the event tells the listener which of those input kinds it is looking at. What *is* available is `ev.workflowContext().instanceData().input()`: for CE-triggered starts, the SDK's `JacksonModelFactory.from(CloudEvent ce)` converts the **entire CloudEvent** (not just `ce.getData()`) into this model via `JacksonCloudEventUtils.toJsonNode` (a plain `ObjectMapper.convertValue` of the whole event), so CloudEvents context and extension attributes — `id`, `source`, `specversion`, `type`, and `traceparent`/`tracestate` — survive as top-level JSON fields on it. `WorkflowMutableInstance.start()` fires `WorkflowStartedEvent` *before* any workflow-defined `input.from`/`input.schema` transform runs, so that raw, unmodified model is exactly what `onWorkflowStarted` sees. Recognizing that model as CloudEvent-derived — so the listener knows to look for `traceparent` on it rather than on an arbitrary payload — is the only reason Phase 1 inspects the input shape at all; it is not re-validating the event. See Phase 1.

### Problem 2 — Trace context is not persisted, so resumed instances have no trace at all

`WorkflowInstrumentationContext` keeps the OTel context as **in-memory-only** workflow instance metadata (`OTEL_CONTEXT` key). None of the persistence backends (`persistence/jpa`, and by extension any other persistence module) store it. After an application restart, `FlowPersistenceRestore.restoreInstances` calls `instance.start()` on rehydrated instances with no `OTEL_CONTEXT` metadata present, so `OTelWorkflowExecutionListener` logs a warning and proceeds with **no span at all** for the rest of that instance's lifecycle.

This isn't a gap Quarkus Flow can close unilaterally: the vendored SDK has no supported way for a `WorkflowExecutionListener` to persist cross-cutting instance metadata across a restart without polluting the workflow's own data model. That gap is tracked upstream as [open-workflow-specification/sdk-java#1645](https://github.com/open-workflow-specification/sdk-java/issues/1645) ("Cross-cutting data attached to a workflow instance by `WorkflowExecutionListener` should survive process restarts"), open at the time of writing with no accepted design yet. Phase 3 is blocked on it.

### Problem 3 — No correlation between flow logs and whatever span is active

`TraceLoggerExecutionListener` (the task-level DEBUG/INFO logger, e.g. "Task 'finishTask' started...") is a self-contained MDC logger with its own keys (`quarkus.flow.instanceId`, `quarkus.flow.taskPos`, etc.). It never reads `Span.current()`, so its log lines carry no `traceId`/`spanId` even in cases where a span genuinely is active — there's no way to pivot from a flow log line to the matching trace in the trace visualizer.

### Related — event correlation direction (design principle, not a bug fix)

`OTelEmittedEventDecorator` already injects the current span context into **outbound** emitted CloudEvents (`TextMapPropagator.inject`). There is no inbound counterpart (`TextMapPropagator.extract`) anywhere in the repo — correlated/`listen` events never have their own trace context read or used. When this is implemented, it must **not** re-parent the workflow's ongoing spans onto the correlated event's trace (see Alternatives Considered — this would fragment the very trace continuity this ADR restores, break `join`/multi-event correlation which has no single valid parent, and let sampling decisions leak in from unrelated producers). Instead, the correlated event's extracted `SpanContext` should be attached as a **span link** on the task span that consumes it, preserving one continuous trace per workflow instance while still letting a viewer pivot to the producer's trace via the link.

## Decision

Implement in four independent, separately shippable phases. Each phase closes one problem above and can land as its own PR.

### Phase 1 — CloudEvent `traceparent` fallback for the workflow root span

**Goal:** the workflow's root span becomes a genuine child of the triggering CloudEvent's trace whenever the CloudEvent carries a `traceparent` extension attribute, and falls back to a documented, correct new-root behavior when it doesn't.

- In `OTelWorkflowExecutionListener.onWorkflowStarted`, read `ev.workflowContext().instanceData().input()` via `WorkflowModel.as(JsonNode.class)` and first recognize whether the node is CloudEvent-derived — the four CloudEvents v1.0 required context attributes present (`id`, `source`, `specversion`, `type`) — before treating any field on it as a CloudEvent extension. Only once that passes, look for top-level `traceparent`/`tracestate` fields (per the CloudEvents Distributed Tracing extension spec's structured-mode JSON encoding) and extract a parent via `GlobalOpenTelemetry.getPropagators().getTextMapPropagator().extract(...)`, before falling back to `Context.current()` and finally a genuine new root span. This reads the raw, pre-`inputFilter` workflow input model — confirmed via `WorkflowMutableInstance.start()`/`startExecution` that the started event fires before any input transform runs — so it works for *any* CE-triggered start (any connector, any `AbstractTypeConsumer` implementation), independent of whether the receiving connector has OTel instrumentation. No `CloudEvent` object is needed and no new dependency is introduced anywhere: this stays entirely inside `opentelemetry/runtime`, which already depends on `opentelemetry-api` and (transitively, via `serverlessworkflow-impl-core`) Jackson. See Alternatives Considered for why this reads the input model instead of intercepting earlier in `FlowMessagingConsumer`.
- Order of precedence for the workflow root span's parent: (1) `traceparent`/`tracestate` parsed from the raw input JSON, only when that JSON is recognizably CloudEvent-derived and the value is well-formed, (2) `Context.current()`, when non-empty (covers connectors, e.g. Kafka, that already propagate a live ambient `Context`, and non-CE-triggered starts invoked from within an already-traced call), (3) new root span (current behavior, now an explicit, logged choice rather than a silent side effect).
- **This shape check is a trigger discriminator, not a CloudEvent validator — it does not duplicate the CE SDK's validation.** CloudEvent well-formedness is already enforced upstream: `FlowMessagingConsumer` (and anything built on the SDK's `AbstractTypeConsumer`) hands the engine an `io.cloudevents.CloudEvent` that the connector's CloudEvent codec has already parsed and validated, and a malformed event is rejected there — `msg.nack(...)` — before any workflow instance is created. By the time `onWorkflowStarted` runs, a CloudEvent-derived input is necessarily valid. The listener only needs to answer a question the `WorkflowStartedEvent` does **not** carry: was this instance triggered by a CloudEvent at all, or by a plain `String`/`Number`/domain object that must not be probed for a `traceparent`. A presence check of the four required attribute names on the `JsonNode` answers exactly that; re-deserializing the input into an `io.cloudevents.CloudEvent` through the CE SDK's `EventFormat` on every workflow start would spend parsing cost to re-derive a guarantee that already holds.
- The four-attribute check (rather than looking at `traceparent` alone) also closes the only remaining false-positive path: a non-CloudEvent workflow input that happens to carry a field literally named `traceparent`. An arbitrary payload that *also* carries `id`, `source`, `specversion`, and `type` as siblings is a practical impossibility, so this is treated as closed rather than as an accepted risk.

### Phase 2 — Correlate flow logs with the active trace

- Introduce a small neutral SPI in `core/runtime`, e.g. `io.quarkiverse.flow.tracing.TraceCorrelationProvider`, with a single method returning plain `String` `traceId`/`spanId` values (no OTel types in the signature). `core/runtime` stays OTel-agnostic; it only knows this interface.
- `TraceLoggerExecutionListener.withMdc` looks up an optional CDI bean of that interface (`Instance<TraceCorrelationProvider>`, guarded by `isResolvable()` — the same optional-lookup pattern `WorkflowApplicationCreator` already uses for `Instance<WorkflowExecutionListener>`) and, when present and a span is actually active, adds `traceId`/`spanId` to the MDC alongside the existing `quarkus.flow.*` keys (no synthetic/placeholder trace IDs when there is none).
- `opentelemetry/runtime` supplies the only implementation: a CDI bean that reads `Span.current().getSpanContext()` and returns plain strings. The OTel dependency stays confined to `opentelemetry/runtime`, exactly like `OTelWorkflowExecutionListener` is confined there today — `core/runtime` never gains a `quarkus-opentelemetry`/`opentelemetry-api` dependency, and the bean is simply absent (so `isResolvable()` is `false`) when the OTel extension isn't installed.
- This makes every flow-specific log line directly greppable/joinable with the trace visualizer by `traceId`, closing the "how do I relate a span to a flow log line" gap, independent of whether Phase 1's propagation succeeded for a given event.

### Phase 3 — Persist trace context for resumed instances (blocked on upstream)

**Status:** blocked on [open-workflow-specification/sdk-java#1645](https://github.com/open-workflow-specification/sdk-java/issues/1645). 

Quarkus Flow has no supported way to carry `WorkflowInstrumentationContext`'s OTel metadata across a restart today without either polluting the workflow's own data model
or forking the vendored SDK (Non-Goals) — that upstream issue is open, with no accepted design yet, and this ADR does not prescribe what the SDK's mechanism should look like; 
that's the SDK maintainers' decision. 

Phase 3 is limited to the one commitment that's ours to make regardless of the upstream mechanism's shape:

- Once sdk-java exposes a supported way for listener-attached cross-cutting instance data to survive a restart, Quarkus Flow will use it to carry the current span context through to `FlowPersistenceRestore.restoreInstances` (as a W3C `traceparent` string, consistent with Phase 1's representation). 
This applies uniformly across all persistence backends (`persistence/jpa` and any other module implementing persistence) — none is exempted or deferred to a later follow-up once the upstream mechanism lands.
- On restore, the semantic decided below (see Alternatives Considered — "Keeping the original root span open across a restart") holds regardless of the upstream mechanism's shape: start a new span for the *resumed portion* of execution, **linked** (not parented — the original trace's root span already ended when the process stopped) to the original trace's span context.
- Instances without persisted trace data — whether because they predate this feature or because the upstream mechanism hasn't landed yet — simply keep today's behavior (warning + no span).

### Phase 4 — Span-based correlation for inbound events during execution

- Add `TextMapPropagator.extract(...)` handling for CloudEvents consumed during workflow execution (e.g. `listen` tasks), mirroring the existing outbound `OTelEmittedEventDecorator` injection.
- The extracted `SpanContext` is attached as a **link** on the task span that processes the correlated event — never as that span's parent. This is what keeps a `join`/fan-in task (multiple correlated events, each potentially from a different producer trace) representable: N links, one parent (the workflow's own ongoing trace).

## Consequences

- **Positive:** a CloudEvent-triggered workflow shows up as one continuous trace from HTTP ingress through every task, matching what the user already expected from the trace visualizer screenshot. Flow logs become directly correlatable to traces. Resumed instances will remain observable (linked, not fully re-parented, which is the correct semantic after a process restart) once Phase 3 ships.
- **Positive:** the new-root-span fallback (Phase 1, precedence rule 3) stops being an unlogged accident and becomes an intentional, visible code path — useful for genuinely disconnected triggers (e.g. a scheduled/cron-started workflow with no upstream trace at all).
- **Blocked:** Phase 3 cannot ship until [open-workflow-specification/sdk-java#1645](https://github.com/open-workflow-specification/sdk-java/issues/1645) lands upstream — there's no persistence mechanism to build against yet, and this ADR intentionally doesn't pre-suppose one. Phases 1, 2, and 4 don't depend on it and can ship independently.
- **Trade-off:** Phase 1 reads `traceparent`/`tracestate` out of the workflow's raw input JSON rather than a `CloudEvent` object (none is reachable at `onWorkflowStarted`), so it needs a cheap way to tell a CloudEvent-triggered start apart from a start on an arbitrary payload before trusting any extension field. It uses a presence check for the four required CloudEvents v1.0 context attributes (`id`, `source`, `specversion`, `type`). This is trigger discrimination, not CloudEvent validation — the CE SDK already validated the event upstream at the connector boundary and rejected malformed ones before any instance started, so the listener is not re-doing that work. A non-CloudEvent input carrying a field named `traceparent` *and* all four of those attribute names as siblings is the only false-positive path, and is treated as closed rather than as an accepted risk.
- **Trade-off:** Phase 1's CloudEvent `traceparent` fallback only works if the producer stamped the extension attribute in the first place — this is opt-in on the producer's side per the CloudEvents spec, not something Quarkus Flow can enforce. For the specific `quarkus-reactive-messaging-http` case reported, the real fix (the connector making a live `Context` current per request, matching Kafka's behavior) has been filed upstream as [quarkiverse/quarkus-reactive-messaging-http#442](https://github.com/quarkiverse/quarkus-reactive-messaging-http/issues/442); until/unless that lands, the `traceparent`-extraction fallback remains the only path to unbroken traces for HTTP-triggered workflows.
- **No breaking changes:** all four phases are additive; existing workflows without any of this metadata behave exactly as they do today (empty-context new root span, no persisted trace, no MDC trace fields).

## Alternatives Considered

### Re-parenting the workflow span onto each correlated event's trace (Phase 4)

Considered and rejected. Re-parenting would mean the workflow's remaining execution becomes a "child" of whichever event last correlated in — semantically wrong (the workflow instance existed before and independently of that event), and mechanically broken for `join` tasks waiting on multiple events from different producers (a span has exactly one parent). It also lets an unrelated producer's sampling decision override the workflow's own, causing workflow traces to intermittently vanish. Span links (chosen instead) are OTel's purpose-built mechanism for exactly this "causally related, not parent-child" relationship — the same pattern used for message-queue consumer spans in the OTel messaging semantic conventions.

### Keeping the original root span open across a restart (Phase 3)

Considered and rejected. A span's lifetime is bound to a process; a span left "open" in persisted state across a restart (potentially hours or days) would report a misleading duration and break span-close semantics most backends assume. Starting a new, linked span for the resumed portion keeps durations meaningful while preserving traceability back to the original execution via the link. This is a semantic decision Quarkus Flow can make now, independent of whatever persistence mechanism [open-workflow-specification/sdk-java#1645](https://github.com/open-workflow-specification/sdk-java/issues/1645) eventually provides — it governs how the restored context gets used, not how it gets stored.

### Wrapping the `ManagedExecutor` hop in `FlowMessagingConsumer` with a captured `Context`

Considered and rejected as out of scope for this ADR. `FlowMessagingConsumer` hands CloudEvents off to a `ManagedExecutor` (`executor.runAsync(() -> dispatch(ce))`); an earlier draft of this design proposed capturing `Context.current()` before that hop and restoring it on the executor thread via OTel's `Context.wrap(Runnable)`/`.wrap(Executor)`. Testing showed this would only ever help connectors that *already* make a live `Context` current before invoking `@Incoming` — confirmed true for Kafka, whose consumer records run inside a Vert.x duplicated context carrying Quarkus's own Kafka consumer span, propagated across the executor hop today via MicroProfile Context Propagation's Vert.x-aware `ThreadContextProvider`. There is nothing for that hop to lose on the Kafka path already. `quarkus-reactive-messaging-http`, the connector behind the reported bug, never establishes a live `Context` in the first place (tracked upstream as [quarkiverse/quarkus-reactive-messaging-http#442](https://github.com/quarkiverse/quarkus-reactive-messaging-http/issues/442) — see Non-Goals), so wrapping the executor submission would have nothing to capture and would not have fixed the reported bug. It would also have required a new `quarkus-opentelemetry` dependency on `messaging/runtime`, which has none today. The CloudEvent `traceparent` extraction fallback (Phase 1, as decided) is the only mechanism that helps regardless of the receiving connector's instrumentation, since it reads context the producer stamped into the event payload itself — so it was kept as Phase 1's sole scope, and the executor-hop change was dropped rather than shipped as an ineffective addition.

### Round-tripping the input through the CE SDK to detect a CloudEvent (Phase 1)

Considered and rejected. Instead of a field-name presence check, `onWorkflowStarted` could hand the input `JsonNode` to the CloudEvents SDK (`io.cloudevents.jackson` / `EventFormat.deserialize`) and treat "parses as a `CloudEvent`" as the signal. This is the spec-compliant way to answer "is this a valid CloudEvent" — but that is not the question at this point. Validity is already guaranteed: the connector's CloudEvent codec parsed and validated the event before `FlowMessagingConsumer` handed it to the engine, and malformed events were `nack`ed before any instance was created (see Phase 1). The listener only needs to discriminate the *trigger kind* (CloudEvent vs. a plain `String`/`Number`/domain object), and a full re-deserialization into a `CloudEvent` object on every workflow start — including the majority that were never CloudEvent-triggered — pays allocation and parsing cost to re-establish a guarantee that already holds. The presence check is O(4 map lookups) and allocates nothing. It stays the decision; the CE SDK path would only make sense if the SDK stopped validating at the connector boundary, which would be a larger regression than this ADR addresses.

### Extracting `traceparent` in `FlowMessagingConsumer` instead of `OTelWorkflowExecutionListener` (Phase 1)

Considered, and not the current decision, but left **open** rather than rejected. `FlowMessagingConsumer.dispatch(CloudEvent ce)` is the last point in quarkus-flow's own code where the raw `CloudEvent` object (with real `.getExtension("traceparent")` access) is guaranteed available before the SDK converts it into a `WorkflowModel`. 
Extracting there was considered instead of parsing the converted input JSON in `onWorkflowStarted` (as Phase 1 now does), but has three costs the input-JSON approach avoids: 
(1) `messaging/runtime` and `opentelemetry/runtime` share no common quarkus-flow module today (both depend directly on `serverlessworkflow-impl-core` only), so this would need either a new `opentelemetry-api` dependency on `messaging/runtime` or a new shared SPI module; 
(2) `dispatch(ce)` fans out to *both* new-instance-start registrations and `listen`/correlation registrations on already-running instances (`AbstractTypeConsumer.CloudEventConsumer.accept` iterates all matching registrations without distinguishing them) — making the extracted context "current" around the whole `dispatch()` call risks it leaking into an in-flight task span's parenting during a `listen` match, which is exactly the re-parenting anti-pattern rejected above for Phase 4; 
(3) `FlowMessagingConsumer`/`AbstractTypeConsumer` are base classes users can replace with their own consumer implementation, so any extraction logic embedded there would be silently lost for applications that swap in a custom consumer, whereas listening on `WorkflowStartedEvent` (as Phase 1 does) applies uniformly regardless of which consumer delivered the event — this could be mitigated with a strategy pattern (an interface a custom consumer implementation is expected to invoke, rather than requiring inheritance from the base classes), but that adds an SPI surface Phase 1's listener-based approach doesn't need in the first place. 
`onWorkflowStarted`, by contrast, only ever fires once per new instance, so reading the input model there is inherently scoped to the new-instance-start case with no such risk. 
This alternative stays open for revisiting if a future `WorkflowModel` factory implementation doesn't preserve CloudEvent extension attributes onto the model the way `JacksonModelFactory` does today.
