# GenAI Semantic Convention Attributes on Agentic Workflow Spans - Design Specification

**Date:** 2026-10-30
**Status:** Proposed
**Issue:** [#1122](https://github.com/quarkiverse/quarkus-flow/issues/1122)
**Related:** [#1056](https://github.com/quarkiverse/quarkus-flow/issues/1056), [#1065](https://github.com/quarkiverse/quarkus-flow/pull/1065), [ADR 2026-10-07 agentic trace context propagation](2026-10-07-opentelemetry-agentic-trace-context-propagation.md)

## Context

`quarkus-flow-opentelemetry` emits `workflow.execute <name>` and `task.execute <name>` spans that carry only `flow.*` attributes. Now that trace context propagates through agentic topologies (#1056), the workflows generated by `quarkus-flow-langchain4j` for `@SequenceAgent`, `@ParallelAgent`, `@ConditionalAgent` and `@LoopAgent` sit in the same trace as the model calls they drive. GenAI-aware observability backends still can't tell what those workflow spans are:

- Some backends keep or export only spans that carry a `gen_ai.*` attribute, plus ancestors of such spans found in the **same export batch**. A `workflow.execute` span ends after its children, often in a later batch (and a workflow that waits can live for a long time), so it gets dropped even though it has AI children.
- Backends that classify spans from `gen_ai.operation.name` (`invoke_agent`, `chat`, `execute_tool`) show Flow's spans as generic spans.

The application-side workaround is a `SpanProcessor` that stamps `gen_ai.operation.name=invoke_agent` in `onStart`. It has no reliable way to recognize an agentic workflow: it rebuilds the agent interface's class name from Flow's kebab-case `flow.workflow.namespace`/`flow.workflow.name` and checks it for an agentic annotation by reflection. That depends on Flow's naming and won't work in native mode.

### Why the existing metadata is not enough

`AgenticFlow` can write the `io.quarkiverse.flow.invoker.*` keys (bean, method, params, kind) to the workflow document metadata. These exist for DevUI, which uses them to invoke the agent method. `AgenticFlow.invocationMetadata()` returns nothing unless `invokerMethodName()` is overridden, and `FlowLangChain4jProcessor` generates that override only when the launch mode is dev or test. **In production the workflow document carries no marker at all.** (The issue says the marker is also missing in tests. For `@QuarkusTest` it is present, so integration tests alone can't prove the production behavior.)

## Decision

### 1. A dedicated agent marker in the workflow document metadata

Introduce a document-metadata key, `io.quarkiverse.flow.agent.name`, whose value is the agent's name. Its presence means "this workflow is an agent invocation".

- It is independent of the DevUI invoker keys and is written in **every** launch mode.
- It lives in `core/runtime` as `WorkflowAgentMetadata` in `io.quarkiverse.flow.internal`, next to `WorkflowInvocationMetadata`. It provides a writer for the fluent `DocumentBuilder.WorkflowMetadataBuilder` and an `Optional`-returning reader that accepts only non-blank strings.
- `quarkus-flow-opentelemetry` reads it from `WorkflowDefinitionData.workflow()`. The OTel module gains no dependency on `quarkus-flow-langchain4j`; both modules already depend on core.

### 2. Generated agentic workflows always set the marker

- At build time, the LangChain4j processor resolves the agent name: the agentic annotation's `name` attribute, or the annotated method's name when that is blank. This mirrors LangChain4j's own agent naming.
- The generated `AgenticFlow` subclass always exposes the agent name, not only inside the dev/test-only invoker block. Workflows built at runtime through `FlowAgentsBuilderService` fall back to the simple name of the agent interface.
- `AgenticFlow.buildDocument()` always applies the agent marker, and still applies the DevUI invoker metadata when it is available.

### 3. Plain workflows opt in with the same key

A hand-written Java DSL or YAML workflow becomes an `invoke_agent` span by setting `io.quarkiverse.flow.agent.name` in its `document.metadata`. There is no configuration property. The choice belongs to the workflow and travels with its definition.

### 4. Stamp the `workflow.execute` span of agent workflows

When the marker is present, `SpanBuilderFactory.newWorkflowExecuteSpan` adds:

| Attribute | Value |
|---|---|
| `gen_ai.operation.name` | `invoke_agent` |
| `gen_ai.agent.name` | marker value |
| `gen_ai.agent.description` | `document.summary`, only when non-blank (generated agentic workflows put the agent description there) |

This one place covers both the first execution and resumption after a restart, because both go through the same factory method.

These spans are not stamped:

- `workflow.create`: it does no agent work.
- `task.execute`, except agent tasks (Decision 5): a plain Java step is not an agent, and the conventions have no operation name for "a step". Backend-specific typing stays in the backend's own integration.
- Workflows without the marker.

### 5. Agent tasks from the Java DSL

In a hand-written workflow the agent invocation is often a single task, created with the Java DSL `agent(..)`, rather than the whole workflow. Here the task is the invocation, so its span is typed, not the workflow's:

- `agent(..)` marks its task with the task-metadata flag `io.quarkiverse.flow.agent.task=true`. `withUniqueId(..)`, which `agent(..)` builds on, stays unmarked. The flag is merged into any existing task metadata.
- When the flag is present, `SpanBuilderFactory.newTaskSpan` sets `gen_ai.operation.name=invoke_agent` and `gen_ai.agent.name` to the task name. A task has no summary, so there is no description.
- The workflow containing agent tasks is not typed, unless it is an agent itself. A workflow can hold several agent tasks, and the conventions model each invocation as its own span.
- The flag is a boolean rather than a name, because the task name already identifies the agent and unnamed tasks get their name only when the task list is built.
- The sub-agent tasks of generated agentic workflows are plain function tasks and stay unflagged. A sub-agent that is itself a composite agent is a generated workflow with its own `invoke_agent` span, so flagging the task too would nest two agent spans for one invocation.
- Detecting agent calls inside arbitrary task bodies, for example by introspecting flows that inject agents, is out of scope.

### 6. Use the semconv incubating constants

The attribute keys and the `invoke_agent` value come from `io.opentelemetry.semconv:opentelemetry-semconv-incubating` (`GenAiIncubatingAttributes`). `quarkus-opentelemetry` already depends on it and the Quarkus BOM manages its version, so declaring it explicitly in `opentelemetry/runtime` adds no new artifact to applications.

## Consequences

### Positive

- GenAI-aware backends keep and classify agentic workflow spans in every launch mode, including native, with no application code.
- The marker is a single, documented contract that plain workflows can also use.
- Existing `flow.*` attributes and span names are unchanged, so existing dashboards and queries keep working.

### Negative / risks

- **Missing `gen_ai.provider.name`.** The conventions require it on `invoke_agent` spans, but a workflow that orchestrates several agents has no single provider. Flow omits it and documents this as a known deviation. The model (`chat`) spans underneath carry the real provider.
- **Span name differs from the convention.** The conventions suggest `invoke_agent {gen_ai.agent.name}`. Flow keeps `workflow.execute <name>` for backwards compatibility. Backends that classify by attribute aren't affected.
- **Incubating conventions.** The GenAI attribute names may change. Using the semconv constants means a semconv upgrade surfaces renames at compile time. The docs flag the attributes as following incubating conventions.
- **The metadata keys become public contract** (`io.quarkiverse.flow.agent.name` on workflows, `io.quarkiverse.flow.agent.task` on tasks) even though their helper lives in an `internal` package. Renaming them later would be a breaking change for opted-in workflows.
- **No duplicate agent spans today.** `quarkus-langchain4j-agentic` 1.14.2 does not emit `invoke_agent` spans for declarative composite agents. If it starts to, the two would need to be reconciled.

## Alternatives Considered

1. **Write the DevUI invoker metadata in every mode and key off `io.quarkiverse.flow.invoker.kind`.** Rejected. It puts bean and method FQCNs into production workflow documents only to be used as a flag, ties observability to a DevUI concern, and gives no natural agent name or opt-in path for plain workflows.
2. **Detect agentic workflows from names or reflection in the OTel module** (the current application workaround). Rejected. It's fragile against naming changes, needs a dependency or reflection on LangChain4j annotations, and is native-unfriendly.
3. **A configuration property listing the workflows to type as agents** (e.g. `quarkus.flow.otel.genai.workflows`). Rejected. It matches by name, duplicates what the definition can say about itself, and adds config surface. Per-workflow metadata covers the use case.
4. **Rename agentic workflow spans to `invoke_agent <name>`.** Rejected for now because it breaks existing span-name based queries. It can be revisited behind a flag if backends need it.
5. **Hardcode the `gen_ai.*` strings.** Rejected. The incubating artifact is already on the classpath, and its constants catch upstream renames at compile time.
6. **Also type plain `task.execute` spans** (e.g. as `execute_tool`). Rejected. Plain steps are not tools or agents in GenAI terms, and mislabeling them would distort backend views. Tasks created with `agent(..)` are agent invocations and are typed (Decision 5).
7. **Mark the whole workflow when it contains an `agent(..)` task.** Rejected. The workflow is not the agent, a workflow can contain several agent tasks with no single agent name, and the task span is the one that wraps the agent's model calls.

## Testing Strategy

- OTel runtime unit tests on `SpanBuilderFactory`: stamped with the marker, unstamped without it, a blank marker ignored, `workflow.create` never stamped.
- A LangChain4j runtime test showing that an `AgenticFlow` **without** the dev/test invoker overrides (the production shape) still writes the marker.
- Core DSL tests: `agent(..)` flags its task, `withUniqueId(..)` does not, and the flag keeps existing task metadata.
- OTel runtime unit tests on agent task spans: a flagged task is typed with its task name, and a plain task is not.
- OTel integration tests (`AgenticTraceContextIT`): both generated workflows of `sequence(classify, parallel(details, summary))` are typed `invoke_agent` with the expected agent names, their task spans are not typed, a plain workflow is not typed, an opted-in Java DSL workflow is typed, and in a Java DSL workflow only the `agent(..)` task span is typed.
